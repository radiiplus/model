| Titans | Paper proposes a neural long-term memory updated online from surprise/gradient, in addition to attention short-term memory. ## Prototype and method

The [preserved Transformer](../experiments/tiny_gpt.py) was not edited. The comparison uses the same `d_model=32`, four heads, `d_ff=128`, context 128, one layer and tied output. A fresh Transformer task model has 17,888 parameters. The standalone [RetentionGPT](../experiments/sequence_mixers.py) replaces only the attention mixer with a normalized recurrent K/V outer-product state, adds the same learned position table, and has the same 17,888 parameters. It is an educational RetNet-like recurrence, not a reproduction of TorchScale RetNet. The independent fixture/training/latency code is [`sequence_mixer_benchmark.py`](../experiments/sequence_mixer_benchmark.py); source and result hashes are in [`sequence_mixer_manifest.json`](../experiments/sequence_mixer_manifest.json).

Three deterministic synthetic tasks were trained from scratch for 80 steps each with seeds 101, 202 and 303: a periodic next-token string; parity of 31 input bits followed by a query marker; and recall of one of seven exact payload IDs after a variable number of filler IDs. Training examples have length 32 and batch 4. Parity is tested at lengths 8, 32, 64 and 128. Copy is tested at delays 1, 4, 8, 16, 29, 32, 64 and 125, with 28 balanced examples per distance. Because the 80-step copy models remained at chance, a separate 300-step copy-only follow-up was run with the same seeds and preserved separately.

The recurrence implemented is `S_t = gamma_h * S_(t-1) + k_t outer v_t`, `z_t = gamma_h*z_(t-1)+1`, `y_t = (q_t S_t / z_t)/sqrt(d_head)` per head. Four fixed decays are `[0.50,0.80,0.90,0.99]`. State shape is `[B,H,d_head,d_head]` plus `[B,H,1,1]` scale; for batch 1 and float32 this is 1,040 bytes, independent of T. This normalization is the prototype's choice, not TorchScale's exact recurrence. Training prefill is sequential in Python/Torch steps; this is intentionally simple and not a fused or chunkwise RetNet kernel.

Reproduce, each under a 120-second timeout and a 2.5 GiB `MemAvailable` guard:

```sh
timeout 120s env OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 NUMEXPR_NUM_THREADS=1 PYTHONDONTWRITEBYTECODE=1 /tmp/b4-torch-venv/bin/python research/experiments/sequence_mixer_benchmark.py --config research/experiments/baseline_config.json --output research/experiments/results/sequence_mixer_tiny.json --steps 80 --seeds 101 202 303 --repeats 5
timeout 120s env OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1 NUMEXPR_NUM_THREADS=1 PYTHONDONTWRITEBYTECODE=1 /tmp/b4-torch-venv/bin/python research/experiments/sequence_mixer_benchmark.py --config research/experiments/baseline_config.json --output research/experiments/results/sequence_mixer_copy_followup.json --steps 300 --seeds 101 202 303 --repeats 5 --tasks copy_exact_token
```

## Local measurements

These are our measurements, not paper or repository claims. The full 18-run, three-seed comparison took 27.44 seconds, peak RSS 366,149,632 bytes, with 5,304 MiB available at start. The 300-step copy follow-up took 32.53 seconds and peaked at 357,617,664 bytes RSS. Both used one Torch thread, CPU float32 and the already installed isolated PyTorch 2.15.0+cpu environment.

| Metric | Transformer | Recurrent retention | Scope |
|---|---:|---:|---|
| Parameters | 17,888 | 17,888 | Matched exactly; same embeddings, MLP and norms |
| Periodic next-token exact accuracy | 1.00, all 3 seeds | 1.00, all 3 seeds | 80 training steps; narrow memorized pattern |
| Parity accuracy at length 32 | 0.552 mean | 0.552 mean | 32 random test sequences/seed; weak task performance |
| Parity accuracy at length 64 | 0.583 mean | 0.365 mean | One retention seed scored 0/32; high seed variance |
| Copy accuracy after 80 steps | 0.143-0.190 by distance | 0.143 at every distance | Seven-way chance is 0.143; neither had learned copy |
| Copy accuracy after 300-step follow-up | 0.857 at distances 4-125; 0.905 at distance 1 | 0.095-0.143 across distances | Transformer learned; retention stayed near chance. This is a failure of this training/configuration, not proof about RetNet generally. |
| Prefill at T=32 / 64 / 128 | 0.57 / 0.60 / 0.94 ms | 7.15 / 16.72 / 30.01 ms | Mean of 5 CPU calls; retention implementation loops over tokens in Python |
| Prefill time per token at T=32 / 64 / 128 | 0.0178 / 0.0094 / 0.0073 ms | 0.223 / 0.261 / 0.234 ms | Derived from the measured prefill totals above; do not compare as an optimized-kernel result |
| One-token decode at T=32 / 64 / 128 | 0.53 / 0.59 / 0.88 ms | 0.21 / 0.19 / 0.29 ms | Transformer recomputes entire prefix; retention uses saved recurrence state. Not an optimized KV-cache Transformer comparison. |
| Persistent state/cache at T=32 / 64 / 128 | Actual code: no cache; hypothetical MHA KV 8,192 / 16,384 / 32,768 bytes | 1,040 / 1,040 / 1,040 bytes | float32, batch 1, one layer; excludes model parameters and temporary activations |
| Training time per 80-step task run | 0.21-0.22 s | 2.59-2.72 s | Batch 4, sequence 32; recurrence has many small eager ops |

Retention state does not grow with sequence length, but this CPU implementation has much slower prefill/training than the Transformer and failed to learn exact copy under the tested optimizer and step budget. Its one-token recurrent update is faster than full-prefix recomputation in this uncached Transformer. That does not establish an inference win against a Transformer with an actual KV cache or fused kernels. In parity, results are low and variable; no reliable task winner is established.

The 300-step copy result has substantial seed variation: Transformer accuracy at each delay from 4 through 125 was `[0.571, 1.000, 1.000]` across the three seeds; retention was `[0.143, 0.143, 0.143]`. At delay 1, Transformer was `[0.714, 1.000, 1.000]`, retention again `[0.143, 0.143, 0.143]`. Thus even the Transformer result is preliminary, and the tested recurrence's failure should be read as a reason to investigate its recipe and state update, not as a general family comparison.

## Upstream Test Coverage

- Mamba's [`test_selective_scan`](https://github.com/state-spaces/mamba/blob/e9594ce1c732d97440f0332fdc43170a2294dbfa/tests/ops/test_selective_scan.py#L38), Triton state-update tests and generation tests hard-code CUDA. Mamba-3 variable-length tests skip without CUDA. They do not verify the pure-Torch reference as a CPU fallback.
- RWKV-7 has no focused test suite in the inspected tree. `rwkv_v7_numpy.py` contains a one-off verification block that loads a hard-coded external `.pth` checkpoint and compares logits; it is not hermetic and does not test streaming continuation or checkpoint round-trip.
- TorchScale's `tests/test_decoder.py::test_decoder` covers generic Decoder configurations, not `RetNetDecoder`; no RetNet recurrent state, incremental continuation or checkpoint round-trip tests were found.
- xLSTM has useful [`test_recurrent_vs_chunkwise_native`](https://github.com/NX-AI/xlstm/blob/ab22eadbd245f293dd8dec38ed29963d73758a12/tests/test_chunkwise_vs_recurrent.py) coverage for output/state equivalence, but the shared test template moves tensors to CUDA. CPU weight-conversion and mocked loader tests exist; neither is a real checkpoint round-trip.
- S4's [Cauchy](https://github.com/state-spaces/s4/blob/e757cef57d89e448c413de7325ed5601aceaac13/extensions/kernels/test_cauchy.py#L28) and [Vandermonde](https://github.com/state-spaces/s4/blob/e757cef57d89e448c413de7325ed5601aceaac13/extensions/kernels/test_vandermonde.py#L15) kernel tests hard-code CUDA; no focused `step` versus sequence-forward equivalence test was found. Safari has synthetic training configs, but no focused Hyena unit/recurrent test; its recurrence remains unimplemented.
- Our own recurrence smoke tests check equal model parameter count, full-forward versus token-step equality, actual state shape/bytes and fixture encodings. They passed 3/3. The unchanged Batch 4 model tests passed 4/4 and evaluation harness tests passed 5/5.

## Failure cases and shortlist

- **Keep unchanged:** Batch 4 Transformer remains the reference baseline. Do not overwrite its config, source, checkpoint or result.
- **Retain as a research prototype, not a chosen architecture:** the normalized retention recurrence makes state-memory reduction concrete and enables one-token recurrent updates. It failed to learn retrieval in the current recipe, and its serial CPU prefill is slow. Next test should diagnose optimizer/scale and content-addressable recall before adding complexity.
- **Defer Mamba:** official fused path is CUDA-dependent; the Transformers pure-Torch scan is a candidate for an independent small reproduction, but its intermediate memory and serial CPU cost need measurement.
- **Defer RWKV-7:** source has a CPU NumPy reference and fixed matrix state, but full source/config and CPU benchmark are not justified yet; do not download its example checkpoint.
- **Defer S4 and Hyena:** useful parallel sequence processing, but FFT/dependency cost and, for Hyena, absent recurrent path leave generation unresolved.
- **Reject xLSTM for reuse at present:** community/commercial license terms and CUDA-oriented default make it a poor project dependency until licensing and CPU path are settled.
- **Keep GQA/MQA as a distinct later ablation:** it can shrink KV cache but memory still grows with T. Sliding-window attention is a deliberate loss of long-range direct retrieval; ALiBi changes position bias only.
- **Defer Titans and Zoology code:** Titans lacks canonical official implementation in this audit; Zoology's license was unresolved. Do not treat paper headlines or synthetic benchmark claims as reproduced evidence.

The unresolved central question is whether a recurrent compressed state can preserve precise, adversarially queried information at a meaningful CPU compute advantage after a fair training recipe. The current 300-step experiment did not answer that affirmatively: the Transformer learned the copy task and this normalized retention version did not.
