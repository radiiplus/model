# Tokenizer and Input-Representation Landscape

Checked 2026-11-23. Repository revisions, exact paths and candidate status are recorded in `../REPOSITORY_LEDGER.csv`. No pretrained tokenizer vocabulary/model checkpoint was downloaded. The local run used only synthetic text and small tokenizer packages; paper statements below remain author-reported and no model result was reproduced.

## Evidence classes

- **Source observations** come from the pinned repository files and public APIs listed below.
- **Paper claims** are results reported by the cited authors for their particular architecture, data, evaluation and compute budget.
- **Our measurements** are only the seven held-out synthetic records in `../experiments/results/tokenizer_benchmark.json`.
- Tokenization method and input architecture are separate decisions. Byte-level BPE merges bytes into a learned fixed vocabulary; it still requires a tokenizer. Byte IDs and Unicode codepoints are unsegmented input representations. Patch-based architectures add learned/dynamic grouping inside the network.

## Reading the local measurement

The fixture is 18 small, project-authored synthetic strings. The split reserves seven held-out records (numbers, code, Unicode equations, URL, rare emoji string, mixed scripts and punctuation) from 11 training records. All methods round-trip the 629 held-out UTF-8 bytes exactly. The benchmark configures byte fallback/identity normalization for SentencePiece to separate segmentation from normalization loss.

Measured held-out results in this environment:

| Method | Effective vocabulary | Tokens / UTF-8 byte | Attention-pair proxy vs bytes | Train time | Encode throughput | Exact roundtrip |
|---|---:|---:|---:|---:|---:|---|
| UTF-8 byte IDs | 256 | 1.000 | 1.000 | negligible | 286 MB/s | Yes |
| Unicode codepoint IDs | 1,112,064 theoretical | 0.846 | 0.684 | negligible | 129 MB/s | Yes |
| Hugging Face ByteLevel BPE | 393 (requested max 512) | 0.844 | 0.747 | 0.0033 s | 31.3 MB/s | Yes |
| SentencePiece BPE, byte fallback | 512 | 0.838 | 0.738 | 0.0130 s | 38.2 MB/s | Yes |
| SentencePiece Unigram, byte fallback | 500 | 0.846 | 0.745 | 0.0058 s | 66.9 MB/s | Yes |
| tiktoken educational byte BPE | 512 | 0.827 | 0.716 | 0.141 s | 4.21 MB/s | Yes |

The attention-pair proxy is `sum(tokens_i^2) / sum(UTF8_bytes_i^2)` across documents. It approximates quadratic self-attention work only for equal per-layer architecture and unpadded per-document sequences; it ignores padding, batching, MLP work and kernel effects. Linear sequence work ratio is simply held-out token count / byte count. The codepoint “vocabulary” is the 1,112,064 Unicode scalar value space; only 532 codepoint IDs were emitted on held-out text. The SentencePiece fallback fraction is measured by `<0xNN>` pieces; for tiktoken educational BPE it is base byte-rank tokens. Hugging Face ByteLevel BPE represents bytes by its alphabet, so a fallback fraction is not meaningful.

These timing numbers are noisy microbenchmarks on seven short strings. Rust/C++ libraries and a Python educational reference implementation are not runtime-equivalent. Vocabulary compression does not establish lower training loss, better reasoning, factuality, code quality or robustness. This run is a representation/serialization smoke test only.

## Recommendation candidates (not a selection)

1. Keep UTF-8 bytes as the correctness/coverage baseline (256 IDs); test whether longer sequences erase the representation's simplicity under a fixed compute budget.
2. Compare one byte-level BPE and SentencePiece Unigram as the practical fixed-vocabulary candidates. Keep the trainer, regex, normalization, byte fallback and special-token IDs versioned.
3. Treat Unicode codepoint IDs as a conceptual baseline, not a direct large-softmax design; investigate hashed/bucketed embeddings only in a later architecture batch.
4. Defer BLT/SpaceByte/MEGABYTE/Charformer-style internal patching until a small architecture test can distinguish patching gains from parameter/compute changes. Some implementations have unresolved or restrictive licenses.

## Required model-training ablation

To test whether a tokenizer helps, use identical raw training text and held-out raw text, a frozen train/validation split, same training seed(s), optimizer and data ordering. Compare (a) byte IDs, (b) one byte-BPE, (c) SentencePiece Unigram, and optionally (d) codepoints. Reserve byte fallback to keep coverage comparable and pin normalization so no method silently changes content. Report two separate views: equal raw bytes seen and equal measured training FLOPs/compute, since token counts differ. Match the non-embedding model body parameter budget and report embedding/output parameters separately; also report total parameters, batch sequence lengths, padding, throughput, peak memory and total update count. Evaluate per-track task scores, bits per UTF-8 byte (not only per-token loss), code/math, multilingual/rare strings, exact copy and noisy-input behavior with multiple seeds. If it fits only one run, mark it preliminary. Do not call fewer tokens or lower per-token loss “better” without downstream gains at a comparable parameter/compute budget.
