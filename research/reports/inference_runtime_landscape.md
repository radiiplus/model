## Separate execution and model changes

Quantization, mmap, optimized kernels, KV caching, batching and speculative decoding change how a model is represented or executed. They should preserve the model's intended distribution or be evaluated as behavior changes. Architectural changes (new learned heads, altered precision during training, early-exit training, ternary weights) can change model outputs and require task-quality evaluation. A faster token loop is not itself a quality improvement; fewer bytes do not establish preserved capability.

## Local CPU profile

The untouched 14,816-parameter, one-layer TinyGPT baseline was loaded from its Batch 4 checkpoint and exported to an inference-only PyTorch state file. We compared FP32 against the installed x86 PyTorch CPU dynamic-`qint8` conversion on the four `nn.Linear` modules. This is not GGUF, GPTQ, AWQ, BitNet, or a universal weight-only quant format. Embeddings, tied output projection, LayerNorm, activations and KV state stayed FP32. PyTorch emitted a deprecation warning for `torch.ao.quantization.quantize_dynamic` and points users to torchao APIs; this is a bounded compatibility measurement, not the recommended long-term API.

| Artifact | Size |
|---|---:|
| Existing training checkpoint (includes optimizer state) | 197,919 B |
| FP32 inference-only checkpoint | 66,107 B |
| Dynamic INT8 inference-only checkpoint | 31,323 B |
| Model state tensors only, serialized | FP32 64,691 B; INT8 30,747 B |

INT8 file size fell 52.6% here, less than 4x because the embeddings and tied head remain FP32 and quantization metadata/packing add overhead. This file-size result is not a process-RSS reduction measurement: both models were loaded in one process and shared runtime overhead, with 345,866,240 bytes peak RSS. The run started with 5,356 MiB available and ended in about 1.51 s. No memory pressure occurred.

Across the training sequence and five deterministic synthetic probes (61 target tokens), FP32 and INT8 both had 24.6% next-token accuracy and identical argmax IDs. Mean logit absolute error was 0.0154 and maximum 0.2051. This is a tiny-token probe only; it cannot establish held-out quality preservation. FP32 prefill was 0.40-0.61 ms and dynamic INT8 prefill 0.49-0.83 ms for contexts 8-32 in this run; sub-millisecond timings varied across repeats and shapes, so no robust throughput win is claimed. The model is too small for optimized kernels to amortize conversion/dispatch costs.

The manually implemented FP32 KV path matches full-prefix forward: prefill max logit error 0; one-token next-step max error 1.43e-6. KV cache state is `[batch, heads, time, head_dim]` for K and V. Measured theoretical cache storage for this one-layer model is 256 bytes per context token: 2,048 B at T=8; 4,096 B at T=16; 6,144 B at T=24; 8,192 B at T=32. With 10 repeats, cached decode-only transitions took about 0.26-0.32 ms/token (roughly 3,100-3,900 transitions/s) at prefix lengths 8-24, versus about 0.48-0.59 ms/token (roughly 1,700-2,100 transitions/s) when recomputing the full prefix; the recurrent Python cache prototype showed a local advantage for this model. The INT8 version remained slower than FP32 and its cache/recompute timing was also noisy. Shared-prefix two-branch timing did not show a large stable win at these sizes. These values exclude initial prefill for decode-only figures; prefill is reported separately. They compare eager PyTorch paths, not optimized GGML or a production KV implementation.

A separate fresh Python process importing PyTorch took 1.592 s (`time` shell measurement); the filesystem page cache was warm, so this is a process-start/import proxy, not a true cold-start measurement. The timed local checkpoint load took 3.34 ms for FP32 and 7.38 ms for INT8 including quantized-module wrapping; files were already in the OS page cache. At this toy scale, import/allocator startup dominates model loading.

## Cache and memory accounting

For a dense decoder with MHA/GQA KV state, approximate KV bytes are:

`2 * batch * layers * context_tokens * n_kv_heads * head_dim * bytes_per_element`

Actual layout, padding, block allocation, sliding-window attention, shared-prefix state, quantization scales and allocator overhead change this estimate. Example: 12 layers, 4 KV heads, head dim 64, 4,096 tokens, batch 1, FP16 cache is about 48 MiB. GQA reduces the cache in proportion to KV-head count; weight quantization alone does not reduce KV storage. A server's cache reservation can exceed the model weights, so cap it from device memory, batch, context and expected concurrency rather than trusting a large runtime default.

KV/prompt cache is reusable state, not free persistent compute: it consumes memory and must be invalidated on changes to model, adapters, prompt prefix, position/cache policy or request isolation. A CPU prompt cache may help repeated long prefixes; for short contexts, lookup/copy/serialization overhead can exceed recomputation. Benchmark shared-prefix hits and misses, cache memory, and eviction separately.

## Consumer profiles and conversion plan

1. **Portable CPU, single user:** keep the canonical training checkpoint in FP32/BF16; use a supported native reference first. Once architecture and exporter are validated, convert a copy to GGUF; test FP16/BF16, Q8, Q5 and Q4 types with `llama.cpp`, compare the exact tokenizer/template and logit/task suite, and use mmap + one/two threads with an explicit context. Consider Q4_K_M or Q5 only if held-out behavior and per-task metrics justify the loss. Pin the runtime commit and GGUF metadata.
2. **Apple Silicon:** maintain a separately validated MLX-LM export and native cache/profile; do not infer from Linux CPU measurements.
3. **Consumer GPU:** choose a runtime after hardware and throughput target are known: llama.cpp for broad backends, ExLlamaV3 for supported quantized CUDA cards, and vLLM when continuous batching/server throughput pays for its memory and dependency cost. Compare single-request latency separately from batched throughput.
4. **Very low-bit specialized model:** BitNet/bitnet.cpp is an architecture/training/runtime branch, not a post-hoc free compression switch for today's dense Transformer. Evaluate only after training a model in the compatible weight representation.

Keep an unquantized source checkpoint and hash every export. Quantize only once from the high-precision model; avoid repeated requantization. Use a small calibration set for activation-aware methods and an independently held-out data/task set for quality. Measure model-only bytes, load peak RSS, resident RSS, prefill, steady one-token decode, KV bytes by context/batch, prompt-cache hit/miss, output tokens/sec, task metrics and error distribution. A successful tensor load is not enough: validate tokenization, position offsets, tied embeddings, logits, greedy IDs and exact code/math tests. Save conversion environment and per-tensor dtype map.

## Deferred tests and limitations

- No GGUF converter or inference runtime was installed/built because the custom one-layer model is not known to be supported by its architecture converter. Native PyTorch is the honest local baseline.
- No proper calibration benchmark with downstream held-out data exists yet. A quantized model needs exact capability/abstention tests and repeated examples before choosing a format.
- No GPU, Apple Silicon, ARM, long-context, concurrent serving or power/energy profile was measured.
- Speculative methods were not implemented: the model has one layer, no useful smaller draft, and no trained early-exit/tree head. At this size the verifier cannot amortize an auxiliary pass fairly. LayerSkip/Medusa/EAGLE remain source-level research candidates, not tested accelerations.
- `llama.cpp` reports substantial quantized file-size examples and offers CPU/GPU backends, mmap, multiple K/V cache dtypes and prompt caching; those upstream claims are not results for this model. Hardware-specific speed and quantization quality must be measured on target devices.
